## A. Residual-stack diagnosis

We want to decide the next TPU experiment. JAX uses BF16 weights and activations.
The diagnostic creates `h[0] = jit(prefix)(states)`, then
`h[d+1] = jit(block[d])(h[d])`; reference output is `jit(head)(h[10])`.
For each depth it separately compiles `suffix[d] = jit(blocks[d:] + head)`.
A Pallas prefix output `p[d]` is passed to `suffix[d]` and compared with that
reference. At depth 1: hidden cosine .999991, hidden mean absolute difference
.000545, final-output mean absolute difference .17224 and argmax agreement .7301.
BF16 and FP32-statistics variants print identical max/mean/RMSE summaries at one
depth. Dense source A uses `(x @ w) + bias` in BF16; source B has an FP32 matmul
accumulator, adds FP32 bias and then converts to BF16.

What does this establish, and what compact combined experiment should run next?

## B. Beam promotion

A replacement scores all moves of each parent. The search executes:
`scores = scores.at[invalid].set(+inf)`;
`values, ids = lax.top_k(-scores.reshape(-1), beam_width)`.
The new full model is 15% faster, finite, and has 99.9% row-wise argmax agreement.
Inputs were generated by drawing each of 150 integer entries independently from
`[0,150)`. The actual puzzle state represents a permutation. A colleague suggests
declaring the implementation search-equivalent and promoting it. Decide and
specify the minimum relevant acceptance measurements; include ties and masking.

## C. Memory and alignment

We have an older `pallas_call` TPU kernel with a logical activation width 130,
stored as width 256. It performs Dense, LayerNorm and ReLU; affine parameters
are padded. The author computes LayerNorm over all 256 storage elements, then
slices to 130. They ask whether zero padding makes this equivalent. They also
want one universal block-shape rule and VMEM budget usable on v3 and newer TPU.
`interpret=True` passes locally. Explain what should be fixed or checked before
a hardware run, including what local interpretation establishes.

## D. Performance interpretation

A dense microbenchmark improved 1.5x, but BM/BK/BN all changed along with fusion.
On a matched tile the improvement is 2.2%. A full model with per-layer fusion
runs at .547 M states/s; the original JAX model runs at 1.386 M states/s. These
two runs use the same checkpoint and batch. An eight-device independent-shard
benchmark with fixed batch per device has 96% parallel efficiency. No collective
or search stages are inside its timer. Which implementation should be the
current reference, what claims are supported, and what would you measure next?

## E. Runtime and pipeline design

The log contains `TFRT_TPU_0`, requested accelerator `v3-8`, and compiler scoped
VMEM limit `16.00 MiB`. The developer proposes treating that as complete hardware
inventory, copying CUDA warp/stream scheduling into Pallas, selecting `pl.ANY`
to force weights into HBM, and adding two explicit buffers to hide all loads.
JAX is 0.10.2 in the job; the local runtime is 0.10.1. The current web tutorial
uses `pl.kernel` while the code uses `pl.pallas_call`. Advise on implementation
and the evidence required before stating that loads overlap compute.

## F. Constants and experiment maintenance

An A/B has both original JAX and Pallas wrappers closing over their weights.

is compile-rejected for VMEM; one is numerically invalid but fastest.
How should these results affect the next implementation and the reusable TPU
