# TPU Builders program work

Use this skill for TPU Builders membership, monthly activity reports, credit requests, and related onboarding. Read [references/program.md](references/program.md) for the last verified process and links. Reopen the current handbook and forms before acting because fields and policies can change.

## Activity reports

Collect the actual activity dates and links to public code, notebooks, benchmarks, tutorials, talks, or demos. Distinguish completed work from planned work and local tests from TPU execution. Write concise English summaries that put the result first, name the Google products actually used, and include 3–5 relevant tags if the form offers them. Check title, links, dates, and scope before submission. Save confirmation and submitted text; do not submit duplicate reports for the same activity unless asked.

## Credit requests

Read the live credit form and inspect the signed-in Cloud project and billing account. Use only the real project ID, project number, and billing account ID shown by Google Cloud. Describe the workload, TPU resources, expected duration, and public outputs using project evidence. Estimate the requested dollars from current TPU prices when possible. The handbook recommends an initial $1,000 request, but the form and project needs govern the amount. If billing is absent, prepare the request and identify the exact missing step; do not invent an ID or imply credits are already approved.

Before using the Cloud console, distinguish requesting program credits from enabling billable services. Check the live account state, expected cost, and whether a payment method or legal agreement is involved. Follow the active computer-use confirmation requirements for those actions. A budget alert is only a notification and does not cap spend.

## Evidence and follow-up

Record the source URL, date checked, submission confirmation, pending approvals, and next action. Keep nonpublic account identifiers and billing details out of public repositories. Do not copy the members-only handbook into a public plugin; link to it and summarize operational requirements. When program staff ask for updates, use the latest project ledger and verified hardware results, then send only what the user authorized.
